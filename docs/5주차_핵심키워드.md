## 1. SOP와 CORS

### 1-1. 출처(Origin)란?
- **Origin = 스킴(프로토콜) + 호스트 + 포트**
  - `https://www.example.com:443/foo` → Origin은 `https://www.example.com:443` (경로 `/foo`는 포함되지 않음)
  - 기본 포트는 생략 가능: `https://www.example.com` = `https://www.example.com:443`
- 셋 중 **하나라도 다르면 다른 출처(cross-origin)** 다.

| 기준: `http://localhost:5173` | 같은 출처? | 이유 |
|---|---|---|
| `http://localhost:5173/members` | O | 경로는 Origin에 포함되지 않음 |
| `http://localhost:8080` | **X** | 포트 다름 → **오늘 실습의 프론트 ↔ Spring 관계** |
| `https://localhost:5173` | X | 스킴 다름 |
| `http://127.0.0.1:5173` | X | 같은 PC여도 호스트 문자열이 다름 |

### 1-2. SOP (Same-Origin Policy, 동일 출처 정책)
- **정의**: 한 출처에서 로드된 문서/스크립트가 **다른 출처의 리소스(응답)를 읽는 것을 제한**하는 브라우저의 기본 보안 정책
- **왜 필요한가?** 브라우저는 요청을 보낼 때 해당 사이트의 쿠키를 자동으로 실어 보낸다. SOP가 없다면:
  1. 사용자가 `bank.com`에 로그인한 상태로 `evil.com`에 접속
  2. `evil.com`의 JS가 `fetch("https://bank.com/my-account")` 호출 → 브라우저가 bank.com 쿠키를 자동 첨부
  3. `evil.com`이 **내 계좌 정보 응답을 그대로 읽어 감**
  → SOP는 3번의 "**응답 읽기**"를 막는다.
- 주의: `<img src>`, `<script src>`, `<link>`, form 제출처럼 **다른 출처로 요청을 "보내는 것" 자체는 원래 허용**된다. SOP가 막는 핵심은 **JS가 응답을 읽는 것**이다.

### 1-3. CORS (Cross-Origin Resource Sharing, 교차 출처 리소스 공유)
- **정의**: SOP의 예외를 만들기 위한 **HTTP 헤더 기반 규약**. 서버가 응답 헤더로 "이 출처는 내 응답을 읽어도 된다"고 밝히면 브라우저가 응답을 JS에 넘겨준다.
- 즉, **허락은 서버가 하고 검사·차단은 브라우저가 한다.**

#### (1) 단순 요청 (Simple Request) — Preflight 없음
아래 조건을 **모두** 만족하면 브라우저가 바로 본 요청을 보낸다. (출처: MDN)
- 메서드: `GET`, `HEAD`, `POST` 중 하나
- 직접 설정한 헤더: `Accept`, `Accept-Language`, `Content-Language`, `Content-Type`, `Range` 만
- `Content-Type`: `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` 중 하나

```
1) 브라우저 → 서버  GET /members/nickname/noco
                    Origin: http://localhost:5173          ← 브라우저가 자동 첨부
2) 서버: 요청을 정상 처리하고 응답 생성 (서버 로그에는 성공)
3) 서버 → 브라우저  200 OK
                    Access-Control-Allow-Origin: http://localhost:5173
4) 브라우저: 내 Origin이 허용 목록에 있음 → JS에 응답 전달 ✅
             헤더가 없거나 다름 → 응답을 버리고 콘솔에 CORS 에러 ❌
```

#### (2) Preflight Request — 본 요청 전에 OPTIONS로 먼저 허락 받기
단순 요청 조건을 벗어나면 (예: `Content-Type: application/json`인 POST, `Authorization` 헤더, `PATCH`/`DELETE`) 브라우저가 먼저 `OPTIONS` 요청을 보낸다.
```http
OPTIONS /members/1/ratings HTTP/1.1
Origin: http://localhost:5173
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: authorization, content-type
```
서버가 `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`로 허락해야 본 요청이 전송된다. `Access-Control-Max-Age`는 이 preflight 결과를 브라우저가 **몇 초 동안 캐시할지**를 정한다.

#### (3) 인증 정보를 포함한 요청 (Credentialed Request)
`fetch(url, { credentials: "include" })`처럼 쿠키를 함께 보내는 요청은 더 엄격하다.
- 서버는 `Access-Control-Allow-Credentials: true`를 보내야 하고
- `Access-Control-Allow-Origin`에 **와일드카드 `*`를 쓸 수 없다** (정확한 출처를 명시해야 함). `*`이면 브라우저가 응답을 차단한다. (출처: MDN)

### 1-4. Spring에서의 CORS 설정 (오늘 작성한 코드)
```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOrigins("http://localhost:5173")
                .allowedMethods("GET", "POST", "PATCH", "DELETE")
                .allowedHeaders("*");
    }
}
```

| 설정 | 의미 | Spring 기본값 (공식 문서) |
|---|---|---|
| `addMapping("/**")` | 모든 경로에 적용 | - |
| `allowedOrigins` | 허용할 출처 | 모든 출처 |
| `allowedMethods` | 허용할 메서드 | **GET, HEAD, POST** |
| `allowedHeaders` | 허용할 요청 헤더 | 모든 헤더 |
| `allowCredentials` | 쿠키 등 인증 정보 허용 | **비활성화** |
| `maxAge` | preflight 캐시 시간 | **30분** |

- 기본값이 GET/HEAD/POST라서, 6~8주차의 PATCH/DELETE를 위해 **`allowedMethods`를 명시**했다.
- `allowCredentials(true)`를 켜면 `allowedOrigins("*")`는 허용되지 않고, 동적인 출처가 필요하면 **`allowedOriginPatterns`** 를 써야 한다. (출처: Spring Framework Reference)
- 매칭되는 CORS 설정이 없으면 Spring은 CORS 헤더를 붙이지 않고, 그 결과 **브라우저가 거부**한다 → 실습 0의 상황.
- 대안: 컨트롤러/메서드 단위 `@CrossOrigin`, 필터 단위 `CorsFilter`. 서비스 전체에 같은 정책이면 전역 설정이 관리하기 쉽다.

### 1-5. 오늘 실습에서 확인한 것

**① CORS 설정 전 (실습 0)**
- `http://localhost:5173`에서 버튼 클릭 → Console:
  ```
  Access to fetch at 'http://localhost:8080/members/nickname/noco' from origin 'http://localhost:5173'
  has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.
  ```
- Network 탭: Request Headers에 `Origin: http://localhost:5173`은 있지만, Response Headers에 `Access-Control-Allow-Origin`이 **없음**
- 당시엔 API를 아직 만들지 않아 실제 응답은 **404**였는데, 콘솔에는 **CORS 에러만** 보였다 → 브라우저가 응답 자체를 JS에 넘기지 않기 때문에 진짜 원인(404)이 가려진다.

**② CORS 설정 후 (9절)**
- 프론트 코드는 **한 글자도 고치지 않고** 서버에 `WebConfig`만 추가 후 재시작
- Response Headers에 `Access-Control-Allow-Origin: http://localhost:5173`, `Vary: Origin, ...`이 생김
- 화면에 `{"available":true}` 출력 (`noco`는 더미 데이터에 없는 닉네임이므로 사용 가능)
- `GET` + 커스텀 헤더 없음 = **단순 요청**이므로 Network 탭에 `OPTIONS`(preflight) 요청은 나타나지 않음
- `/members/999/ratings` 호출 시에도 CORS 에러 없이 **404 상태와 에러 JSON을 읽을 수 있었다** → CORS는 성공/실패와 무관하게 "응답을 읽을 권한"의 문제

**③ Postman / 네이티브 앱은 왜 괜찮았나?**
- 지금까지 Postman 테스트에선 CORS 에러가 한 번도 없었다. Postman은 브라우저가 아니라 SOP를 적용하지 않기 때문이다.
- Flutter 네이티브 앱(dio/http)도 브라우저가 아니므로 CORS의 적용을 받지 않는다. 단, **Flutter Web**은 브라우저에서 실행되므로 CORS가 적용된다.

### 1-6. 내 정리
- CORS 에러는 "요청이 막힌 것"이 아니라 "**응답 읽기가 막힌 것**"이다. 서버는 이미 처리했다.
- 허용 여부는 **오직 서버의 응답 헤더**로 결정되므로, CORS 에러를 받으면 프론트가 아니라 **백엔드 설정부터 확인**해야 한다.
- `allowedOrigins("*")`는 편하지만 아무 사이트의 JS나 우리 API 응답을 읽게 허용하고, 인증 정보(쿠키)를 쓰는 순간 사용할 수도 없다. 운영 환경에서는 배포된 프론트 도메인만 명시하는 것이 원칙이다.

## 2. Same-Origin과 Same-Site의 차이

### 2-1. 용어 정리 (출처: web.dev)
| 용어 | 정의 | 예: `https://www.example.com:443/foo` |
|---|---|---|
| **Origin** | 스킴 + 호스트 + 포트 | `https://www.example.com:443` |
| **eTLD** | 유효 최상위 도메인. 공용 접미사 목록(Public Suffix List)으로 결정 | `.com` |
| **eTLD+1** | eTLD + 바로 앞 한 단계 | `example.com` |
| **Site** | 스킴 + eTLD+1 | `https://example.com` |

- `.co.kr`, `.github.io`처럼 점이 여러 개인 공용 접미사는 규칙으로 계산할 수 없어서 **Public Suffix List**라는 목록으로 관리한다.
  - `https://my-project.github.io` → eTLD는 `.github.io`, Site는 `https://my-project.github.io`
  - 그래서 `a.github.io`와 `b.github.io`는 **서로 다른 사이트**다 (남의 GitHub Pages가 내 쿠키를 받으면 안 되니까).

### 2-2. Schemeful Same-Site
- 예전에는 eTLD+1만 비교했지만(**schemeless**), 현재는 **스킴까지 같아야** same-site로 본다(**schemeful same-site**).
- 즉 `http://www.example.com`과 `https://www.example.com`은 **cross-site**다.

### 2-3. 비교 표 (기준 A = `https://www.example.com:443`)
| B | Same-Origin | Same-Site | 이유 |
|---|---|---|---|
| `https://www.example.com` | O | O | 기본 포트 443 생략 |
| `https://www.example.com:80` | X | O | 포트만 다름 → Site는 포트 무시 |
| `https://login.example.com` | X | O | 서브도메인 다름 → Site는 서브도메인 무시 |
| `http://www.example.com` | X | **X** | 스킴 다름 (schemeful) |
| `https://www.evil.com` | X | X | eTLD+1 다름 |

### 2-4. 브라우저가 각각을 어디에 쓰나
| | Same-Origin | Same-Site |
|---|---|---|
| 판단 질문 | "이 응답을 JS가 **읽어도** 되나?" | "이 요청에 쿠키를 **실어 보낼까**?" |
| 관련 기능 | SOP, CORS | 쿠키 `SameSite` 속성 |
| 엄격함 | 엄격 (포트·서브도메인까지) | 느슨 (스킴 + eTLD+1만) |

- 참고: 최신 브라우저는 요청마다 `Sec-Fetch-Site` 헤더(`same-origin` / `same-site` / `cross-site` / `none`)를 붙여, 서버가 요청의 출발 위치를 알 수 있게 한다.

### 2-5. 오늘 실습에 대입하면
| A | B | Same-Origin | Same-Site |
|---|---|---|---|
| `http://localhost:5173` (프론트) | `http://localhost:8080` (Spring) | **X** (포트 다름) | **O** (스킴·호스트 같음, 포트 무시) |

→ 우리 프론트와 백엔드는 **same-site지만 cross-origin**이다. 그래서 쿠키 전송 측면에선 같은 사이트로 취급되지만, 응답을 읽으려면 **CORS 허락이 필요**했다.

### 2-6. 내 정리
- 이름은 비슷하지만 **판단 대상이 다르다**: Origin은 "응답 읽기", Site는 "쿠키 전송".
- Site는 포트와 서브도메인을 무시하기 때문에 `www.movie.com`(프론트)과 `api.movie.com`(백엔드)처럼 배포해도 같은 사이트로 묶인다. 하지만 Origin은 다르므로 CORS 설정은 여전히 필요하다.

## 3. 쿠키의 SameSite 속성

### 3-1. 정의와 목적
- **정의**: 쿠키를 설정할 때 "**다른 사이트(cross-site)에서 시작된 요청에도 이 쿠키를 보낼지**"를 지정하는 속성
- **목적**: **CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)** 완화
  - CSRF: 사용자가 `bank.com`에 로그인한 상태에서 `evil.com`의 숨겨진 폼이 `bank.com/transfer`로 POST를 보내면, 브라우저가 bank.com 쿠키를 자동 첨부해 **사용자 모르게 송금**이 실행되는 공격
  - SOP는 "응답 읽기"를 막을 뿐 "요청 보내기"는 막지 않으므로, CSRF는 SOP만으로 막을 수 없다 → 쿠키 단에서 막는 것이 SameSite

### 3-2. 값별 동작 (출처: web.dev)
| 값 | cross-site 요청에 쿠키 전송 | 예시 상황 | 추천 용도 |
|---|---|---|---|
| `Strict` | 보내지 않음 (외부 링크 클릭으로 들어와도 첫 요청엔 미전송) | 다른 사이트의 링크로 들어오면 로그인 안 된 것처럼 보임 | 비밀번호 변경, 결제 등 민감 기능 |
| `Lax` | **최상위 탐색(링크 클릭 등)** 에만 전송, 이미지·iframe·fetch 등 하위 요청엔 미전송 | 외부 링크로 들어와도 로그인 유지, 하지만 숨겨진 요청엔 쿠키 없음 | 일반 로그인 세션 |
| `None` | 항상 전송 (**반드시 `Secure`와 함께**) | 다른 사이트에 임베드된 위젯, 광고, 교차 사이트 로그인 | 서드파티 쿠키가 필요한 경우 |

```http
Set-Cookie: session=abc123; SameSite=Lax; Secure; HttpOnly
```
- `Secure`: HTTPS에서만 전송 / `HttpOnly`: JS(`document.cookie`)에서 접근 불가 → XSS로 인한 탈취 완화

### 3-3. 브라우저 기본값의 변화
- Chrome 80(2020)부터 **SameSite를 지정하지 않은 쿠키는 `Lax`처럼 취급**한다. 그 전에는 모든 요청에 전송되어 CSRF에 취약했다.
- 다만 Chrome의 "기본 Lax"는 명시적 `Lax`보다 조금 관대하게, 일부 최상위 POST 요청에도 쿠키를 허용하는 **임시 완화 조치**가 있었다. 따라서 브라우저마다 동작이 다를 수 있으니 **명시적으로 설정하는 것이 권장**된다.
- SameSite는 CSRF 위험을 줄이지만 **완전한 해결책은 아니다**. 중요한 요청엔 CSRF 토큰 등 추가 방어가 필요하다.

### 3-4. 우리 프로젝트와의 관계
- 7주차 로그인은 쿠키가 아닌 **`Authorization: Bearer <JWT>` 헤더** 방식이다.
- 헤더는 브라우저가 **자동으로 첨부하지 않고** 프론트 코드가 직접 넣어야 하므로, CSRF처럼 "모르는 사이에 자동 첨부"되는 문제가 구조적으로 적다 → SameSite를 직접 설정할 일이 없다.
- 대신 `Authorization` 헤더를 쓰면 **단순 요청 조건을 벗어나 preflight가 발생**하므로, `WebConfig`의 `allowedHeaders("*")`가 필요해진다. (1번 키워드와 연결)

### 3-5. 내 정리
- **SameSite는 Same-Site(2번 키워드) 기준**으로 동작한다. 그래서 `localhost:5173 → localhost:8080` 요청은 same-site라서 `Lax`여도 쿠키가 전송된다.
- 쿠키 기반 인증이면 SameSite + CSRF 토큰을, 헤더(JWT) 기반이면 CORS의 `allowedHeaders`를 신경 써야 한다. **인증 방식에 따라 챙길 보안 설정이 달라진다.**

## 4. 복합 UNIQUE 제약을 사용하는 이유는?

### 4-1. 오늘 만든 스키마
```sql
CREATE TABLE rating (
    ...
    FOREIGN KEY (member_id) REFERENCES member(member_id),
    UNIQUE KEY uk_rating_member_movie (member_id, movie_id)
);
CREATE TABLE favorite (
    ...
    UNIQUE KEY uk_favorite_member_movie (member_id, movie_id)
);
```

### 4-2. 이유 ① 단일 UNIQUE로는 비즈니스 규칙을 표현할 수 없다
요구사항: "같은 사용자가 같은 영화를 중복으로 즐겨찾기(평점)할 수 없다"

| 제약 | 의미 | 결과 |
|---|---|---|
| `UNIQUE(movie_id)` | 영화 하나당 평점 **전체 1개** | X — 수현이 550번에 남기면 민서는 못 남김 |
| `UNIQUE(member_id)` | 회원 하나당 평점 **전체 1개** | X — 영화를 하나밖에 평가 못 함 |
| `UNIQUE(member_id, movie_id)` | **(회원, 영화) 조합**당 1개 | O — 같은 사람 + 같은 영화만 금지 |

오늘 넣은 더미 데이터 `(1, 550)`, `(1, 155)`, `(2, 550)`이 모두 들어갈 수 있었던 이유가 이것이다. 반대로 `(1, 550)`을 한 번 더 INSERT하면:
```
Error Code: 1062. Duplicate entry '1-550' for key 'rating.uk_rating_member_movie'
```

### 4-3. 이유 ② 애플리케이션 검사만으로는 동시 요청을 막을 수 없다 (Race Condition)
6주차에 평점 등록 API를 만들면 Service에서 "이미 있는지" 먼저 확인하게 된다. 그런데:
```
요청 A: exists(1, 550)? → false ─┐
요청 B: exists(1, 550)? → false ─┤  거의 동시에 도착 (버튼 더블클릭)
요청 A: INSERT  → 성공            │
요청 B: INSERT  → 성공 ❌ 중복!   ┘
```
- 두 요청이 "확인"과 "저장" 사이의 틈에 끼어들면 코드 검사는 둘 다 통과한다.
- DB의 UNIQUE 제약은 **INSERT 순간에 DB가 원자적으로 검사**하므로 두 번째 INSERT를 반드시 거부한다 → **데이터 무결성의 최후 방어선**

| 방어 위치 | 역할 |
|---|---|
| Service의 `exists` 검사 | 대부분의 중복을 미리 걸러 **친절한 에러 메시지**(409 등) 제공 |
| DB 복합 UNIQUE | 동시성까지 포함해 **절대 중복이 저장되지 않음을 보장** |

→ 둘 중 하나가 아니라 **둘 다** 필요하다.

### 4-4. 이유 ③ 인덱스 효과 — Leftmost Prefix 규칙
- MySQL에서 UNIQUE 제약은 **고유 인덱스**를 만든다. 그래서 조회 성능에도 영향을 준다.
- 복합 인덱스 `(member_id, movie_id)`는 **왼쪽 컬럼부터 순서대로** 쓰는 조건에서만 사용된다. (출처: MySQL Reference Manual — Multiple-Column Indexes)

| 조건 | 인덱스 사용? |
|---|---|
| `WHERE member_id = 1` | O (가장 왼쪽 컬럼) |
| `WHERE member_id = 1 AND movie_id = 550` | O |
| `WHERE movie_id = 550` | **X** (왼쪽 컬럼 건너뜀) |

- 오늘 만든 `findByMember_MemberIdOrderByRatingIdDesc`는 `WHERE r.member_id = ?` 조건이므로 이 인덱스의 왼쪽 컬럼을 활용할 수 있다. (`member_id`에는 FK 때문에 인덱스가 필요한데, InnoDB는 이미 `member_id`로 시작하는 인덱스가 있으면 그것을 FK 인덱스로 사용한다.)
- 반대로 나중에 "이 영화의 평균 별점"처럼 `movie_id`만으로 조회하는 기능이 생기면, 별도의 `movie_id` 인덱스를 고려해야 한다.
- **설계 팁**: 복합 인덱스의 컬럼 순서는 **가장 자주 단독으로 조회하는 컬럼을 앞에** 둔다.

### 4-5. JPA 엔티티와의 관계
```java
@Table(name = "rating",
       uniqueConstraints = @UniqueConstraint(columnNames = {"member_id", "movie_id"}))
```
- `columnNames`에는 자바 필드명이 아니라 **DB 컬럼명**을 쓴다. (Query Method는 필드명을 쓰는 것과 반대라 헷갈리기 쉬움)
- 오늘 설정인 `ddl-auto: validate`는 테이블/컬럼 존재와 타입은 검사하지만 **UNIQUE 제약까지 검사하지는 않는다.** 그래도 이 어노테이션은 "이 테이블엔 이런 규칙이 있다"는 **설계 의도를 코드에 남기는 문서 역할**을 한다.

### 4-6. 내 정리
- "**누가 + 무엇을** 한 번만"이라는 규칙은 **조합(복합)** 에 거는 제약으로 표현한다.
- 코드 검사는 UX(친절한 메시지)를 위해, DB 제약은 무결성(동시성 포함)을 위해 존재한다.
- 복합 UNIQUE는 인덱스도 만들기 때문에, **컬럼 순서**가 조회 성능에 영향을 준다.

## 5. 외부 Open API 연동 시 API Key를 프론트/백엔드 중 어디에 두어야 안전한가?

### 5-1. 결론: 비밀(secret)이 되어야 하는 키는 백엔드에 둔다
- 프론트엔드 코드(HTML/JS)는 **사용자 브라우저로 전부 다운로드**된다. 개발자 도구 Sources/Network 탭에서 누구나 볼 수 있다.
- `.env`에 넣어도 프론트에선 빌드 시 **번들에 문자열로 포함**된다. Vite 공식 문서도 `VITE_` 접두사 변수는 번들링 후 클라이언트 코드에 노출되므로 **API 키 같은 민감 정보를 넣지 말고**, 비밀은 백엔드나 서버리스 함수로 처리하라고 경고한다.
- 키가 노출되면 다른 사람이 내 키로 호출 → **사용량 한도 소진, 과금 폭탄, 계정 정지** 위험

### 5-2. 구조 비교
```
[프론트 직접 호출]   브라우저 ──(키 포함)──▶ 외부 API        → 키가 브라우저에 노출
[백엔드 프록시]      브라우저 ──▶ 우리 서버 ──(키 포함)──▶ 외부 API  → 키는 서버에만 존재
```

| 위치 | 장점 | 단점 |
|---|---|---|
| 프론트 직접 | 구현 간단, 서버 부하·지연 없음 | 키 노출, 호출 제어 불가 |
| 백엔드 프록시 | 키 은닉 + **캐싱, 호출 횟수 제한(rate limit), 로깅, 응답 가공** 가능 | 서버 코드·비용·지연 증가 |

### 5-3. 백엔드에 둘 때도 지켜야 할 것 — 오늘 실습과 같은 원리
- 코드나 설정 파일에 **직접 쓰지 않고 환경 변수로 주입**한다.
  ```yaml
  # 오늘 작성한 application.yaml
  spring:
    datasource:
      password: ${DB_PASSWORD}   # 값은 IntelliJ 실행 구성(Environment variables)에만 존재
  ```
- 같은 방식으로 외부 API 키도 `tmdb.api-key: ${TMDB_API_KEY}`처럼 주입하면 Git에 올라가지 않는다.
- 운영 환경에서는 서버의 환경 변수나 클라우드 Secret Manager, GitHub Actions Secrets 등을 사용한다.

### 5-4. 이번 프로젝트(TMDB)는 왜 프론트가 직접 호출할까?
- TMDB는 **API Key**(`api_key` 쿼리 파라미터)와 **API Read Access Token**(`Authorization: Bearer` 헤더) 두 가지 인증 수단을 제공하며, 둘의 접근 권한은 같다. (출처: TMDB Developer Docs)
- 영화 목록/상세/검색은 **공개된 영화 정보의 읽기 전용 조회**라 키가 노출돼도 피해 범위가 비교적 작고, 우리 백엔드가 같은 데이터를 한 번 더 감쌀 실익이 적다.
- 즉, 학습 프로젝트에서 구조를 단순하게 하기 위한 **트레이드오프**다. 실서비스라면 호출량이 많아질수록 백엔드 프록시 + 캐싱을 고려할 만하다.
- 반대로 **결제, SMS 발송, 생성형 AI API처럼 호출마다 비용이 들거나 쓰기 권한이 있는 키는 무조건 백엔드**에 둔다.

### 5-5. 판단 체크리스트
| 질문 | 예 → |
|---|---|
| 호출할 때마다 비용이 드는가? | 백엔드 |
| 데이터를 생성/수정/삭제하는 권한이 있는가? | 백엔드 |
| 응답에 다른 사용자의 개인정보가 포함될 수 있는가? | 백엔드 |
| 공개 데이터의 읽기 전용이고, 제공사가 클라이언트 사용을 허용하는가? | 프론트 직접 호출도 가능 (도메인 제한 등 부가 보호 권장) |

### 5-6. 내 정리
- 판단 기준은 "**이 키가 노출되면 누가, 얼마나 피해를 보는가?**"이다.
- 프론트에 들어간 값은 **어떤 방법을 써도 결국 공개된다**고 생각해야 한다. 숨겨야 하는 값은 서버로 보내고, 서버에서도 환경 변수로 분리한다. 오늘 `DB_PASSWORD`를 yaml이 아닌 환경 변수로 분리한 것과 완전히 같은 원리다.

## 부록. 오늘의 트러블슈팅

**⚡ 이슈 No.1 — 간이 프론트 대신 폴더 목록이 표시됨**
- **`이슈`**: `http://localhost:5173` 접속 시 버튼 화면 대신 `Index of 4824s/` 폴더 목록이 표시됨
- **`문제`**: `npx serve`는 **명령을 실행한 현재 폴더**를 정적 서버로 띄운다. 새 터미널이 홈 폴더(`C:\Users\4824s`)에서 시작된 상태로 실행해서, `index.html`이 없는 홈 폴더 전체가 노출됨 (`.ssh` 등 민감 파일 노출 위험)
- **`해결`**: `Ctrl+C`로 즉시 종료 → `cd C:\development\mock-frontend` 후 재실행 (또는 `npx serve -l 5173 C:\development\mock-frontend`처럼 경로 명시)
- **`배운 점`**: 명령 실행 전 터미널 프롬프트의 **현재 경로를 확인**하는 습관

**⚡ 이슈 No.2 — 실습 0에서 404가 CORS 에러에 가려짐**
- **`이슈`**: API가 없어 실제 응답은 404였지만 콘솔에는 CORS 에러만 표시
- **`문제`**: CORS 허용 헤더가 없으면 브라우저가 응답(상태 코드·본문)을 JS에 전달하지 않음
- **`해결`**: CORS 설정 후에는 404도 정상적으로 읽을 수 있었음 → CORS 에러가 보일 때 **서버 로그/Network 탭의 실제 상태 코드**도 함께 확인해야 함
